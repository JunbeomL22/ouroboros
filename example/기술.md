## 1. API 연동 및 레이턴시

### 1.1 거래소별 REST/WebSocket API 스펙

#### Binance API

| 항목 | 사양 |
|------|------|
| **Base Endpoint (Futures)** | `wss://ws-fapi.binance.com/ws-fapi/v1` |
| **메시지 제한** | 10개/초 (초과 시 연결 해제) |
| **스트림 구독** | 최대 1,024개/연결 |
| **연결 비용** | 2 weight |
| **Ping 간격** | 30초 권장, 1분 내 미응답 시 해제 |
| **서버 위치** | AWS Tokyo |

**Rate Limit 위반 시:**
- 429 에러 반환
- `retryAfter` 필드로 재시도 시점 안내
- 반복 위반 시 IP 밴 (2분~3일)

**2026년 1월 변경사항:**
- 서명 요청 시 payload를 percent-encode 후 서명 계산 필수
- 미준수 시 `-1022 INVALID_SIGNATURE` 에러

> **출처:** [Binance WebSocket API](https://developers.binance.com/docs/derivatives/usds-margined-futures/websocket-api-general-info), [Binance Rate Limits](https://developers.binance.com/docs/binance-spot-api-docs/websocket-api/rate-limits)

#### OKX API

| 항목 | 사양 |
|------|------|
| **WebSocket 연결 제한** | 3회/초 (IP 기준) |
| **Rate Limit 공유** | REST와 WebSocket 간 주문 API 공유 |
| **Public REST** | IP 기준 |
| **Private REST** | User ID 기준 |
| **서버 위치** | AWS Hong Kong |

**인증 헤더:**
- `OK-ACCESS-KEY`: API 키
- `OK-ACCESS-SIGN`: Base64 인코딩 서명
- `OK-ACCESS-TIMESTAMP`: UTC 타임스탬프
- `OK-ACCESS-PASSPHRASE`: Passphrase

> **출처:** [OKX API Guide](https://my.okx.com/docs-v5/en/)

#### Bybit API

| 항목 | 사양 |
|------|------|
| **REST API 제한** | 600회/5초/IP |
| **WebSocket 연결** | 500개/5분 |
| **시장 데이터 연결** | 최대 1,000개/IP |
| **배치 주문** | 1~10개 주문/요청 |
| **실행 속도** | Sub-10ms (Unified V5 API) |
| **서버 위치** | AWS Singapore (apse1-az3) |

**특징:**
- WebSocket 시장 데이터 요청은 Rate Limit 미적용
- 배치 주문으로 효율성 극대화 가능

> **출처:** [Bybit API Documentation](https://www.bybit.com/future-activity/en/developer), [Bybit Rate Limits](https://bybit-exchange.github.io/docs/v5/rate-limit)

#### API 스펙 비교표

| 거래소 | WebSocket 제한 | REST/WS Rate Limit | 서버 위치 | 특징 |
|--------|---------------|-------------------|-----------|------|
| **Binance** | 10 msg/초, 1024 스트림 | 공유 (weight 시스템) | AWS Tokyo | 가장 큰 유동성 |
| **OKX** | 3 연결/초 | 주문 API 공유 | AWS Hong Kong | Unified V5 API |
| **Bybit** | WS 미적용 | 분리 (시장데이터) | AWS Singapore | Sub-10ms 실행 |

## 2. 시스템 아키텍처

### 2.1 주문관리시스템(OMS) 설계

#### OMS 핵심 기능

| 기능 | 설명 |
|------|------|
| **주문 추적** | 미체결 주문, ACK/Fill/Reject 처리 |
| **주문 로직** | 슬라이싱, 재시도, 취소 |
| **리스크 체크** | 집중도 제한, 포지션 한도 |
| **라우팅** | 최적 체결 가격 거래소 선택 |
| **백오피스 연동** | 체결 상세 전송 |

> **출처:** [Gemini - Order Management System](https://www.gemini.com/cryptopedia/order-management-system-crypto-trade)

#### 크립토 OMS 특수 고려사항

```
[Strategy Engine] → [OMS] → [Cross-Venue Gateway] → [Exchange APIs]
                      ↓
              [Risk Management]
                      ↓
              [Position Tracking]
```

**크립토 특화 요소:**
- REST API / WebSocket 연결 (FIX 미지원 거래소 다수)
- Cross-Venue Gateway: 멀티 거래소 추상화 레이어
- 전략 엔진에 통합된 오더북 뷰 제공

> **출처:** [Keyrock Algorithmic Trading Systems](https://medium.com/@gwrx2005/abstract-b81d9635b8cb)

#### Rust 기반 OMS 설계

**Rust 선택 이유:**
- 제로 코스트 추상화
- 메모리 안전성 (GC 없음)
- 소유권 모델로 동시성 버그 방지
- 저레이턴시 요구사항 충족

**주요 Rust 트레이딩 프레임워크:**

##### Barter-rs
| 크레이트 | 용도 |
|---------|------|
| `barter` | 트레이딩 엔진, 상태 관리 |
| `barter-data` | 공개 시장 데이터 스트리밍 |
| `barter-execution` | 주문 실행, 개인 계정 데이터 |
| `barter-integration` | REST/WebSocket 통합 프레임워크 |

**아키텍처 특징:**
- 멀티스레드, 확장 가능
- Tokio 기반 I/O
- 메모리 효율적 데이터 구조
- MarketStream/ExecutionClient 인터페이스로 확장성

> **출처:** [Barter-rs GitHub](https://github.com/barter-rs/barter-rs)

#### 고성능 FIX 시스템 (Rust)

**핵심 최적화 요소:**
- TCP + Kernel-bypass (DPDK, io_uring, OpenOnload)
- UDP Multicast (시장 데이터)
- SIMD 최적화 FIX 파서
- 사전 할당 메시지 풀, 링 버퍼
- String interning (동적 할당 제거)

**주요 라이브러리:**
- `tokio-fix`, `quickfix-rs`: FIX 프로토콜
- `nom`, `serde`: 파싱/직렬화
- `crossbeam`: Lock-free 큐

> **출처:** [Building Ultra-High-Speed Trading Systems with FIX API and Rust](https://digitaloneagency.com.au/building-ultra-high-speed-trading-systems-with-fix-api-and-rust-why-it-has-to-be-done-this-way/)

#### Tokio vs 동기 처리

| 방식 | 장점 | 단점 | 권장 |
|------|------|------|------|
| **Tokio (Async)** | 70% 성능 향상 (다중 연결), 확장성 | 레이턴시 불확정성 | 중간 빈도 트레이딩 |
| **동기/저수준** | 결정적 레이턴시 | 확장성 제한 | HFT 최저 레이턴시 |

**Tokio 최적화:**
- CPU 코어 어피니티 핀닝
- 세션별 전용 I/O 스레드
- Back-pressure 제어

> **주의:** 최저 레이턴시가 필수인 HFT에서는 비동기 프레임워크가 예측 불가능한 지연을 유발할 수 있음

> **출처:** [Tokio Tutorial](https://tokio.rs/tokio/tutorial), [Async Frameworks in Real-Time Trading](https://medium.com/@anon.quant/why-one-should-avoid-using-asynchronous-frameworks-like-tokio-in-real-time-trading-systems-663edbf4e961)

> **출처:** [Talos Portfolio & Risk Management](https://www.talos.com/our-solutions/portfolio-and-risk-management), [Elwood Digital Asset Platform](https://www.elwood.io/)

#### Cross Margin vs Isolated Margin

##### Cross Margin (교차 마진)
- **정의**: 전체 계정 잔고가 모든 포지션의 담보로 사용
- **장점**: 단일 포지션 청산 방지, 자본 효율성
- **단점**: 한 포지션 손실이 전체 계정에 영향
- **권장**: 헤지 포트폴리오, 마켓 메이킹

##### Isolated Margin (격리 마진)
- **정의**: 각 포지션에 고정된 담보 할당
- **장점**: 손실 격리, 리스크 제한
- **단점**: 변동성 완충 감소
- **권장**: 고레버리지 방향성 베팅, 초보자

#### 마진 계산 공식

##### 마진 잔고 (Equity)
```
Margin Balance = Wallet Balance + Unrealized PnL (모든 포지션)
```

##### 레버리지
```
Leverage = Notional Exposure / Collateral
```

##### 청산 조건

**Isolated Margin:**
```
(초기 마진 + 미실현 손익) < 유지 마진 → 청산 트리거
```

**Cross Margin:**
```
Cross Margin Equity (Isolated IM 제외) < Cross 유지 마진 → 청산 트리거
```

##### 마진 네팅 (Hedged 포지션)
```
Total Margin Requirement = Max(Long 마진, Short 마진)
```

##### 담보 헤어컷
```
Collateral Haircut = Σ(담보 자산 가치 × Haircut Rate)
```

> **출처:** [Cross Margin - Cube Exchange](https://www.cube.exchange/what-is/cross-margin), [Isolated Margin - Cube Exchange](https://www.cube.exchange/what-is/isolated-margin), [Kraken Margin Management](https://support.kraken.com/articles/4844463246100-margining-liquidations-multi-collateral-derivatives)

## 3. 데이터 파이프라인

### 3.1 오더북/체결 데이터 수집 및 저장

#### 데이터 수집 방식

##### 실시간 스트리밍
- **WebSocket**: 표준 실시간 시장 데이터 API
- **거래소 직접 연결**: 정규화된 저레이턴시 스트림

##### 데이터 레벨

| 레벨 | 내용 | 용도 |
|------|------|------|
| **L1** | Best Bid/Ask | 현재 시장 상황 파악 |
| **L2** | 상위 N 호가 (예: Top 20) | 일반 분석, 백테스팅 |
| **L3** | Full Depth (전체 오더북) | 정밀 재구성, HFT |

> **출처:** [CoinAPI - Order Book Data](https://www.coinapi.io/blog/full-order-book-data-in-crypto)

#### 데이터 전달 옵션

| 방식 | 특징 |
|------|------|
| **REST API** | 시간별/특정 타임스탬프 조회 |
| **WebSocket** | 실시간 스트리밍 |
| **Cloud Storage** | S3, Azure Blob, GCS 직접 전송 |
| **Flat Files** | Full-depth, 순서별 업데이트 포함 |

#### 데이터 정규화 과제

**주요 문제:**
- 거래소별 심볼/스키마 불일치
- 타임스탬프 드리프트
- REST vs WebSocket 동작 차이
- 오더북 델타 이벤트 기반 (시간 기반 아님)
- 무음 데이터 갭

**솔루션:**
- 통합 명명 규칙 (400+ 거래소)
- 마이크로초 타임스탬프 표준화
- Canonical T+1 파이프라인 (히스토리컬)

> **출처:** [CoinAPI - Real-Time Crypto Data Challenges](https://www.coinapi.io/blog/why-real-time-crypto-data-is-harder-than-it-looks)

#### 시계열 데이터베이스 비교

| DB | 아키텍처 | 강점 | 약점 | 권장 용도 |
|----|----------|------|------|----------|
| **QuestDB** | 컬럼 기반, SIMD | 빠른 쿼리, 쉬운 학습 | - | Raw tick 데이터 |
| **ClickHouse** | 컬럼 기반 | 높은 압축, 대용량 배치 | 소규모 배치 비효율 | 분석 워크로드 |
| **TimescaleDB** | PostgreSQL 확장 | 관계형 기능, 생태계 | Raw tick 처리 한계 | 집계 바, 메타데이터 |
| **KDB+** | 벡터 기반 | 결정적 저레이턴시 | 높은 비용, 학습 곡선 | 엔터프라이즈 HFT |

##### 인제스트 성능

| DB | 대용량 배치 (10K+ rows) | 소규모 배치 (<1K rows) |
|----|------------------------|----------------------|
| **ClickHouse** | 4M rows/sec | 비효율적 |
| **TimescaleDB** | 수만 rows/sec | 효율적 |
| **QuestDB** | 고성능 | 고성능 |

> **출처:** [ClickHouse vs TimescaleDB](https://www.tinybird.co/blog/clickhouse-vs-timescaledb), [QuestDB Financial Tick Data](https://questdb.com/blog/ingesting-financial-tick-data-using-time-series-database/), [KX Benchmarking](https://kx.com/blog/benchmarking-kdb-x-vs-questdb-clickhouse-timescaledb-and-influxdb-with-tsbs/)
